# Harness²: Improving AI Agent Performance Without Model Upgrades

Source: [analytics_vidhya](https://www.analyticsvidhya.com/blog/2026/10/harness2-improving-ai-agent-performance/)

When an AI agent fails to complete a task, upgrading the model can seem like the obvious next step. Yet an agent’s performance also depends on how it receives instructions, uses tools, and manages its work. Understanding those factors can reveal opportunities to improve reliability with the model already in place.
Google Research’s Harness² examines that surrounding setup and its role in agent performance. I installed and ran the project to explore the idea firsthand. In this article, I look at the research, the implementation, and what developers can learn from it when building their own agents.
A harness shapes how an AI agent behaves through its prompts, tools, memory, and control loop. But different harnesses excel at different tasks. Claude Code performs better on coding and spreadsheets, while Codex leads on web tasks.
The takeaway: A fixed harness leaves performance on the table.
Harness² aims to close that gap by adapting at test time even for tasks its designers never anticipated.
Letting an agent rewrite its own system prompt sounds promising. In practice, it can make performance worse.
The problem? Every added instruction comes at a cost.
System prompts are processed repeatedly throughout a task. As they grow, they consume more tokens, leaving less room for the actual work.
And when the token budget runs out, the agent may fail before finishing.
Harness² exposes eight components, most of which stay dormant until something triggers them. That is the point: they cost nothing when unused, unlike prompt text.
Why it works: Unlike prompt instructions, these safeguards are enforced by code not just the model’s willingness to follow them.
The hard problem is knowing whether an edit helped. On a benchmark you have an answer key. On a real task you do not.
The signal comes from differences between executions, not from a score against a known answer. That is what lets it run on tasks it has never seen.
The probe step is not ceremony. Without it, performance dropped by about 10%.
Letting the agent edit its own harness and simply trusting the edit was tested, and it was worse than not editing at all.
Tested on three professional benchmarks across four model-harness configurations, using GLM-5 and Gemini 3.5 Flash. A single step improved on the base harness in every configuration tried.

A 2-task run writes 2,360 files holding about 265 KB between them. How much disk that actually occupies depends on the filesystem: ext4 gave 13 MB because each tiny file claims a 4 KB block, while APFS on macOS packed the same run into 0.3 MB. Worth knowing before a benchmark run with hundreds of tasks.

8 and 6 variants across 2 tasks each gives 16 plus 12, which is the 28 the summary reported. The names map onto the algorithm: inv for invariant edits, dom for domain-specific edits, agg or c for compositions.
The research puts the cost at 4 to 20 full agent runs per task. My run landed at 6 to 8 with k=2, which sits at the bottom of that range.
This is the finding I have not seen stated anywhere else, and it matters if you plan to evaluate the project by running the demo.

The demo proves the plumbing works. It does not demonstrate the method.
The recursion loop runs, probes fire, compositions are produced, the library is written and experience is recorded. But the deterministic editors never generate real content, so no harness is meaningfully rewritten. To see that you need model credentials and a real benchmark.
Each task writes an EXPERIENCE.md, and its headings show what the second loop keeps:

Run directories are large and deeply nested. This pulls out the numbers that matter. Not part of the repository.
inspect_run.py
"""
Inspect a harness2 run directory. Written for this article, not part of the repo.
Usage: python inspect_run.py runs/demo
"""
import json
import pathlib
import sys
import collections
root = pathlib.Path(
    sys.argv[1] if len(sys.argv) > 1 else "runs/demo"
)
# --- headline numbers from the run summary -------------------------
summary = root / "demo.json"
if summary.exists():
    d = json.loads(summary.read_text())
    print("RUN SUMMARY")
    for k in (
        "domain",
        "n_tasks",
        "done",
        "failed",
        "execution_count",
        "editor_calls"
    ):
        if k in d:
            print(f"  {k:<16} {d[k]}")
    print()
# --- how many artefacts did a run actually produce? ----------------
files = [
    p for p in root.rglob("*")
    if p.is_file()
]
total_mb = sum(
    p.stat().st_size for p in files
) / 1024**2
print(
    f"ARTEFACTS: {len(files)} files, {total_mb:.1f} MB\n"
)
# --- execution variants, grouped by mode ---------------------------
print("EXECUTIONS PER TASK")
for mode_dir in sorted((root / "executions").glob("*")):
    tasks = sorted(
        p for p in mode_dir.glob("*")
        if p.is_dir()
    )
    if not tasks:
        continue
    variants = sorted(
        p.name for p in tasks[0].glob("*")
        if p.is_dir()
    )
    print(
        f"  {mode_dir.name:<16} "
        f"{len(variants)} variants: {', '.join(variants)}"
    )
print()
# --- which harness components actually got content? ----------------
print("HARNESS COMPONENTS (bytes written)")
sizes = collections.defaultdict(set)
for p in root.rglob("harness/**/*"):
    if p.is_file():
        key = (
            str(p.relative_to(p.parents[1]))
            if p.parent.name != "harness"
            else p.name
        )
        sizes[key].add(p.stat().st_size)
for name, vals in sorted(sizes.items()):
    v = sorted(vals)
    flag = "  <- EMPTY" if v == [0] else ""
    size_display = (
        v[0]
        if len(v) == 1
        else f"{v[0]}-{v[-1]}"
    )
    print(
        f"  {name:<34} {size_display:>8}{flag}"
    )
print()
# --- the harnessing-level memory -----------------------------------
exp = list(root.rglob("EXPERIENCE.md"))
if exp:
    print(
        f"EXPERIENCE.md x{len(exp)}, section headings:"
    )
    for line in exp[0].read_text().splitlines():
        if line.startswith("#"):
            print("  ", line)
One gotcha worth knowing. Re-running the same output directory skips tasks that already finished, which is the intended resume behaviour, but it also rewrites demo.json with execution_count and editor_calls at zero. Harness² is a working implementation of a clear argument. Keep the weights fixed, optimise the scaffolding, and use contrasts between runs instead of ground-truth labels to decide what to keep.
The research behind it is more interesting than the headline numbers. Prompt-stuffing made things worse. Skipping validation made things worse. A competing memory baseline made coding worse. Those negative results are what make the positive ones credible.
The install is clean and the demo runs in seconds without credentials, which makes it cheap to verify the machinery. Just do not mistake that demo for the method: the components it fills in are stubs, and the part the paper is about only shows up once a model is wired in.
