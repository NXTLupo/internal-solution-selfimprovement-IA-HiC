# Claude Code Custom Commands & Skills: Automate Your Workflow

Source: [analytics_vidhya](https://www.analyticsvidhya.com/blog/2026/10/claude-code-custom-commands-skills-automate-your-workflow/)

Every dev team has repeatable setup tasks: spinning up a new project, running a deployment checklist, generating a file structure, or typing the same instructions into Claude again and again. Claude Code helps reduce that friction with slash commands, including built-in commands and custom commands you can define for your own workflows.
These commands turn repeated instructions into quick triggers, making day-to-day development smoother and more consistent. In this article, we’ll explore Claude Code slash commands, understand how skills work, and build a few practical custom commands along the way.
A slash command is a short text trigger, starting with “/”, that runs a predefined action instantly, instead of you typing out a full instruction every time. You’ve likely seen this pattern before in tools like Slack, Notion, or Discord, where typing “/” brings up a menu of quick actions. The idea is simple: turn something you’d otherwise explain in a sentence into a single word you can type in seconds.

Skills are special instructions stored in a markdown files; it can be configured to only be invoked by the user not by Claude. In legacy syntax, this could be achieved with Custom Slash Commands.  This special instruction gets added to the context when invoked, and is meant to be used for tasks that are generally not needed for Claude, it can be something rare like deployment. It lives as a markdown file in .claude/skills/<name>/SKILL.md, and the sub-folder name becomes the command name: so.claude/skills/deploy/SKILL.md becomes /deploy.

--- 
name: new_repo

disable-model-invocation: true
allowed-tools: Bash(ls *) Bash(mkdir *)
---
Create the base project structure in the current working directory:
1. Create a `backend/` folder. If it doesn't already contain anything, add a minimal `.gitkeep` file (or a starter file appropriate to the stack the user mentions, if any) so the folder is tracked.
2. Create a `frontend/` folder the same way.
3. Create a `README.md` at the project root with:
- A title based on the project name (ask the user or infer from context/directory name)
- A one-paragraph description of the project (infer from the task at hand if not explicitly given)
- A "Project Structure" section listing `backend/` and `frontend/` and their purpose
- A "Getting Started" section with placeholder setup instructions for each folder
Do not overwrite existing files or folders — check first with `ls` and only create what's missing. Report back what was created.
