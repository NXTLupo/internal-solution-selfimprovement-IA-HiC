# Rejected approaches

E2.6 (2026-08-21). Adopted from the `.out-of-scope/` knowledge base in
`triage`: a record of what was REJECTED, and why, so the same idea does not get
re-proposed every few sessions.

This is not a backlog. A backlog holds things we intend to do. This holds things we
decided against, which is different and gets lost faster, because a decision not to
build something leaves no artifact behind unless someone writes one.

**Consult this before proposing an approach.** If the idea is here, either cite the
recorded reason and explain what changed, or pick something else. Re-proposing a settled
rejection with no new information costs a full review cycle to reach the same answer.

## Format

One file per rejection, named for the idea. Each carries:

- **What was proposed**, in one or two sentences, in the words the proposer used.
- **When, and by whom** (a session date is enough).
- **Why it was rejected.** The actual reason, not a euphemism. If the reason was cost,
  say cost. If it was that it duplicated something, name the thing.
- **What would change the answer.** This is the most valuable line and the one most
  often missing. A rejection with no reopening condition is a dead end; a rejection with
  one is a decision that can be revisited honestly when the condition arrives.

A rejection whose reopening condition has arrived should be reopened. That is the point
of recording it, and a file here is not a permanent veto.
