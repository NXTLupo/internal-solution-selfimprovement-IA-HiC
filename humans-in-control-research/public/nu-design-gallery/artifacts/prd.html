§01

Problem statement

most important section

38% of first-year applicants attrite from the co-op cycle when they go fourteen days without a reply from any employer; coordinators discover the dropout retrospectively, after the cycle has closed. 5 The current system fires a single template email at day seven — untargeted, unranked, and identical for a student with one open application and a student with seven. 2

The patternfor recovery already exists in peer institutions: Cincinnati flags inactivity at day five and routes the student to a coordinator triage queue ranked by stalled-signal strength. 3 Coordinators at Northeastern manage 180:1 advising loads; only a triage surface — not more office hours — recovers them from batch email and lets them spend time where it matters. 8

The problem is not detection capability. The problem is that the existing detection feeds nothing actionable, and coordinators have no signal-ranked surface to triage from.

§02

User stories

Primary stories · referenced by persona
  1. As J. Liu (Co-op Coordinator), I want to see which of my 180 advisees have stalled at day 5 of inactivity, so I can reach out before they exit the cycle.
  2. As J. Liu, I want each entry to tell me why it was flagged (no activity + open apps < 4), so I trust the queue and don't second-guess it.
  3. As A. Patel (first-year), I want one personal nudge that mentions my actual application count, so it doesn't feel like a mass email.
  4. As D. Chen (VP Adv Ops), I want a weekly cycle metric showing silence-attrition trend, so I know the intervention is working.

Acceptance criteria

Given/when/then format. Three load-bearing criteria gate the v1 release:

ACGiven / When / Then
AC-01Given a student with 0 Handshake activity events in the past 5 days, when their open-application count is < 4, then they appear in the coordinator's triage queue ranked by stalled-signal score.
AC-02Given a queue entry, when the coordinator hovers the "why?" affordance, then the top 3 contributing signals display in plain English within 200 ms.
AC-03Given a coordinator has acted on a queue entry, when they mark it triaged with a route action, then the entry exits the queue and the student receives a personalized nudge referencing their actual application count.

§09

Wireframes & design notes

Two primary surfaces. Conceptual descriptions; high-fidelity comps maintained by Co-op Ops design — see Figma: triage-v1.

Surface 1 · Coordinator triage queue
  • Left rail: queue ranked by stalled-signal score
  • Right pane: detail with "why flagged?" explain
  • Top: filter by major, signal strength threshold
  • One-click "Route to peer mentor" / "Triage personally" / "Snooze 48 h"
Surface 2 · Student nudge (email + mobile push)
  • Subject names the student's current app count
  • One CTA: "Open my pace dashboard"
  • Opt-out footer ("Pause check-ins")
  • Sent inside the 9 p.m.–1 a.m. engagement window
§10

Data & privacy

The triage signal is derived from activity events only (Handshake login, save, application submit) and application counts — never academic record, GPA, course list, or any FERPA-protected attribute. The system writes a single boolean signal ("flagged on/off") plus a derived stalled-signal score (0–100). All inputs and outputs live inside the existing co-op data domain.
