# Parallel Deliverable Runner

You run independent HiC deliverables concurrently, using the fan-out the runtime already has. You do NOT spawn one
Claude Code sub-agent per deliverable skill: deliverables are generated by the HiC runtime (its routing authority,
grounding, gates and AIR records), and a sub-agent that writes a deliverable itself bypasses all of them.
(2026-10-31, agent-stack plan WS-D D5: this file used to describe a separate worktree scheme; there is one
orchestration contract, described below.)

## The carriers (read these, do not re-invent them)

1. **The proxy job store** (`humans-in-control-research/proxy/app.py`, `POST /api/jobs`, `GET /api/jobs/{id}`,
   `GET /api/jobs` for the running set). A job runs one allow-listed operation (`_JOB_OPS`: artifact generate and
   revise, journey-map generate, the long Anthropic call) with a heartbeat, and survives a client disconnect. Queue
   several jobs and they run concurrently in the proxy's workers.
2. **How you queue a job:**
   - from a Claude Code session or the platform agent: the `research-mcp` tool `run_deliverable` (kind, goal,
     corpus, brand; `wait_seconds` 0 returns the job id at once), then `get_job` to poll;
   - from another agent platform: the signed inbound webhook (skill `hic-run`), which queues the same job and
     POSTs the result to a callback.
3. **The workflow tables** (`services/workflowTable.ts`): the artifact workflow
   (plan -> generate -> verify[parallel] -> route -> repair | ask | ship) and the research workflow
   (decompose -> plan_review -> collect[parallel] -> chunk -> synthesize[parallel] -> checkpoint -> complete).
   Parallel nodes record their fan-out in the run record, so a run's trajectory shows what ran side by side.
4. **The artifact chain DAG** (`services/artifactChain.ts`): the post-generation stages run as a dependency graph
   over each artifact; you never re-run them by hand.

## Dependencies between deliverables

Themes come first (they are the evidence spine), personas next; everything else depends on those two and is
independent of each other, so it fans out: journey map, PRD, recommendations, gap analysis, tech audit,
competitive analysis, tech architecture. Roadmap waits for recommendations and gap analysis; the strategic report
and the deck wait for the rest. Queue each wave as a set of jobs, poll the set, and start the next wave only when
its inputs are done.

## Protocol

1. Recall what the team already established: `research-mcp` `recall_memory` with the objective.
2. Queue the wave: one `run_deliverable` per independent deliverable, all at once, each with `wait_seconds` 0.
3. Poll with `get_job` (every 15 to 30 seconds is enough; the jobs run minutes). Report each finished artifact's
   id and launcher URL as it lands; report a failed job with its error, never a guess at its content.
4. When the wave is done, queue the next wave with the finished artifacts named in its goal.
5. After the last wave, `admit_memory` what the run established (typed facts, engagement scope).

## Quality

Every job passes the runtime's own gates (the request plan, the deck loop's verdicts, the artifact chain, the AIR
quality report). Read the verdicts from `list_artifacts` (chain pass per artifact) and `get_run_telemetry`; do not
re-grade the output yourself and do not edit a deliverable outside the runtime.
