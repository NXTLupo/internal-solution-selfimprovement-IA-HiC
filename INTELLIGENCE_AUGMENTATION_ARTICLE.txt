ABSTRACT

This article presents the technical architecture and implementation details of
the NXT Humans Intelligence Augmentation CX Workbench, a distributed
microservices platform designed for comprehensive customer experience analytics.
The platform integrates 14 specialized AI-powered applications through a unified
JSON-RPC 2.0 protocol, with particular emphasis on the Social Research Analytics
application. We demonstrate a novel pipeline combining BERTopic-based
unsupervised topic modeling, transformer-based embeddings, VADER sentiment
analysis, and PostgreSQL pgvector for large-scale semantic search. The system
achieves production-grade performance with 1.5M+ vector embeddings while
maintaining real-time responsiveness through asynchronous processing and
distributed task orchestration. Our architecture represents a significant
advancement in applied customer intelligence systems, bridging academic research
in NLP with production-scale enterprise deployments.

Keywords: Topic Modeling, Sentiment Analysis, Vector Databases, Microservices
Architecture, Customer Experience Analytics, Natural Language Processing, Large
Language Models

1. INTRODUCTION

1.1 Background

Customer experience (CX) analytics has evolved from simple sentiment tracking
to sophisticated multi-modal intelligence platforms capable of processing
diverse data streams including social media, customer reviews, video content,
and structured feedback. Traditional approaches to CX analytics suffer from
several limitations: (1) inability to scale to real-time processing of millions
of data points, (2) lack of semantic understanding beyond keyword matching,
(3) fragmented tooling requiring manual integration, and (4) limited
interpretability of results for business stakeholders.

1.2 Research Contribution

This work presents the NXT Humans Intelligence Augmentation CX Workbench, a
production-deployed system that addresses these challenges through:

First, a distributed microservices architecture using JSON-RPC 2.0 based
protocol enabling seamless tool orchestration across 14 specialized services.
Second, a hybrid ML pipeline combining unsupervised topic modeling (BERTopic),
transformer embeddings (all-mpnet-base-v2), and lexicon-based sentiment
analysis (VADER). Third, scalable vector search using PostgreSQL pgvector
implementation supporting 1.5M+ embeddings with sub-second retrieval. Fourth,
multi-LLM integration through an abstraction layer supporting Claude
(Anthropic), GPT-4 (OpenAI), and Gemini (Google) for diverse reasoning tasks.
Finally, adaptive hyperparameter optimization with dataset-size-aware
clustering parameters for robust topic extraction from 10 to 10,000+ documents.

1.3 Production Deployment Context

Unlike academic prototypes, this system operates in production environments
processing real customer data at scale. The architecture demonstrates practical
solutions to challenges including: real-time WebSocket communication with 100+
concurrent users, asynchronous job processing with progress tracking and
cancellation, multi-tenant data isolation with PostgreSQL row-level security,
container orchestration via Docker Compose with automatic health checks, and
cross-origin resource sharing (CORS) for web-based frontends.

2. SYSTEM ARCHITECTURE

2.1 High-Level Architecture Overview

The Intelligence Augmentation CX Workbench follows a distributed microservices
pattern with clear separation of concerns. The architecture consists of six
primary layers: Browser Client Layer (React 19 + TypeScript 5.7), Launchpad
Service (WebSocket Proxy + Service Discovery using Flask with thread-safe
routing), AI Agent Orchestrator (Claude 3.7 Sonnet + Tool Coordination via
FastAPI + AsyncAnthropic Client), MCP Services Layer (Model Context Protocol
Adapters including Reddit MCP on port 8501, Social MCP on port 8502, Journey
MCP on port 8503, Video MCP on port 8504, and others), Core Services Layer
(Social Research Backend on port 8081, Journey Mapper on port 8080, Video
Analyzer on port 5002, and additional services), and Data Persistence Layer
(PostgreSQL 16 with pgvector Extension storing relational data and 768-
dimensional vector embeddings).

Communication flows from the browser client through the Launchpad service via
HTTP/WebSocket on port 8000, then to the AI Agent Orchestrator via WebSocket
on port 8500, which communicates with MCP services using JSON-RPC 2.0 protocol.
The MCP services connect to core services via HTTP REST, which finally interact
with the data persistence layer.

2.2 Communication Protocol: JSON-RPC 2.0

The system implements JSON-RPC 2.0 (RFC 4627) for standardized tool invocation
between the AI Agent and MCP services. This choice provides several advantages
over REST: batch operations allowing a single request to contain multiple tool
calls, bidirectional communication supporting both request/response and
notification patterns, strict error handling with standardized error codes and
messages, and language-agnostic design as JSON encoding ensures cross-platform
compatibility.

An example tool discovery request follows this structure: the JSON object
contains "jsonrpc" set to "2.0", "id" set to "tools_list_social_0", "method"
set to "tools/list", and an empty "params" object. For tool execution, the
request structure includes "jsonrpc" at "2.0", "id" as
"tool_call_social_topic_abc123", "method" as "tools/call", and "params"
containing "name" set to "social_topic_model" with "arguments" specifying
"subreddit" as "ouraring", "num_posts" as 500, and "summary_limit" as 10.

2.3 Service Discovery and Tool Caching

At startup, the AI Agent Orchestrator (located at mcp-services/agent/app.py
lines 102-231) performs automatic tool discovery through a five-step process.
First, it iterates through all registered MCP services. Second, it sends a
tools/list JSON-RPC request to each service. Third, it caches tool definitions
in memory with service metadata. Fourth, it builds a dynamic system prompt for
Claude with available tools. Finally, it implements a retry mechanism with
three attempts and two-second backoff for resilience.

This approach enables hot-swapping of services without agent restarts and
supports A/B testing of different tool implementations.

3. SOCIAL RESEARCH ANALYTICS PIPELINE

3.1 End-to-End Data Flow

The Social Research Analytics application implements a five-stage pipeline for
transforming raw social media data into actionable customer insights.

Stage 1 (Data Collection) utilizes the Reddit API (PRAW) with rate limiting,
performs recursive comment tree traversal, applies date range filtering based
on Unix timestamps, and processes image URLs with GPT-4o Vision.

Stage 2 (Text Preprocessing & Embedding) removes stopwords using NLTK, scikit-
learn, and custom lists, extracts N-grams (1-3 grams), encodes text using
SentenceTransformer (all-mpnet-base-v2), and produces 768-dimensional dense
vectors.

Stage 3 (Dimensionality Reduction & Clustering) reduces dimensionality from
768 to 5 dimensions using UMAP with cosine metric, performs HDBSCAN clustering
with EOM (Excess of Mass) selection, applies adaptive hyperparameters based on
dataset size, and conducts outlier detection and filtering.

Stage 4 (Topic Extraction & Summarization) scores term importance using TF-IDF,
filters redundancy with lemmatization, selects representative documents, and
generates summaries using LLMs (Claude, GPT, or Gemini).

Stage 5 (Sentiment Analysis & Vector Storage) performs VADER sentiment scoring
per document, aggregates sentiment at the topic level, ingests data into
PostgreSQL with pgvector indexing, and creates IVFFlat indices with 100 lists.

3.2 Architecture Components

Backend Services include the FastAPI Application (internal-solutions-
socialresearch/backend/app/main.py) serving as an async HTTP server with CORS
middleware, the Topic Modeling Module (util/topic_model/BertTopic.py)
containing 1,151 lines of production-hardened topic extraction logic, the
Sentiment Analyzer (util/topic_model/sentiment_analyzer.py) implementing VADER-
based polarity scoring with chunk-based processing, the Vector Database Layer
(util/llm_models/pgvector/pgvector.py) providing PostgreSQL pgvector
integration with SQLAlchemy ORM, and Data Source Adapters (util/data_source/
reddit_fetcher_topic_model.py) using PRAW-based Reddit API client with nested
comment handling.

Frontend Application components include React 19 with TypeScript 5.7 (internal-
solutions-socialresearch/frontend/) providing modern reactive UI, Redux Toolkit
2.6.0 for centralized state management with async thunks, Material-UI 6.4.3 as
the component library with custom theming, D3.js for force-directed graph
visualization of topic relationships, and Vite 6.1.0 as the build tool with
Hot Module Replacement.

Database components include PostgreSQL 16 as the relational database with
advanced indexing, pgvector Extension for native vector similarity search using
SIMD operations, and schema tables including reddit_posts, reddit_comments,
reddit_embeddings, and jobs.

4. MACHINE LEARNING MODELS AND ALGORITHMS

4.1 Topic Modeling: BERTopic with Adaptive Hyperparameters

The system implements BERTopic (Grootendorst, 2022), a state-of-the-art topic
modeling approach that combines transformers with traditional clustering. Our
implementation extends BERTopic with dataset-size-aware hyperparameter
selection (BertTopic.py lines 695-1059).

4.1.1 Hyperparameter Regimes

For datasets with fewer than 10 documents, UMAP configuration uses n_neighbors
of 3, n_components of 2, min_dist of 0.1, and epochs of 200, while HDBSCAN
uses min_cluster_size of 2 and min_samples of 1. The rationale is extremely
permissive clustering to extract signal from minimal data.

For 10-100 documents, UMAP uses n_neighbors of 3, n_components of 3, min_dist
of 0.15, and epochs of 300, with HDBSCAN using min_cluster_size of 3,
min_samples of 1, and alpha of 1.0. Increased epochs compensate for small
sample size.

For 100-200 documents, UMAP configuration includes n_neighbors of 8,
n_components of 5, and min_dist of 0.07, while HDBSCAN uses min_cluster_size
of 8 and min_samples of 1, providing balanced neighborhood size for moderate
datasets.

For 200-600 documents, UMAP uses n_neighbors of 12, n_components of 4, and
min_dist of 0.05, with HDBSCAN using min_cluster_size of 7 and min_samples of
2, offering standard configuration for typical use cases.

For 600+ documents, UMAP employs n_neighbors of 10, n_components of 5, and
min_dist of 0.05, while HDBSCAN uses min_cluster_size of 5 and min_samples of
3, enabling finer granularity with stricter clustering.

4.1.2 UMAP Dimensionality Reduction

UMAP (Uniform Manifold Approximation and Projection) reduces 768-dimensional
SentenceTransformer embeddings to 2-5 dimensions while preserving local and
global structure. The metric uses cosine similarity, optimal for normalized
embeddings. Random state is fixed at seed 42 for reproducibility. Low memory
mode is enabled for datasets exceeding 1000 documents. Epochs are adaptive,
ranging from 200-300 for small datasets to default 200 for large ones.

The mathematical foundation relies on UMAP optimizing a fuzzy topological
representation by minimizing cross-entropy between high-dimensional and low-
dimensional fuzzy simplicial sets.

4.1.3 HDBSCAN Clustering

HDBSCAN (Hierarchical Density-Based Spatial Clustering of Applications with
Noise) identifies topics as dense regions in the reduced embedding space. Min
cluster size defines documents required to form a topic (adaptive 2-8). Min
samples sets the core point threshold for density (adaptive 1-3). Cluster
selection method uses Excess of Mass (EOM) for stability. The metric employs
Euclidean distance in UMAP space. Prediction data is enabled for soft
clustering of new documents.

The advantage over K-Means is that HDBSCAN automatically determines the number
of topics and identifies outliers, eliminating the need for pre-specifying K.

4.2 Embedding Model: all-mpnet-base-v2

The system uses all-mpnet-base-v2 from Sentence-Transformers (Reimers &
Gurevych, 2019) for document encoding.

Model specifications include architecture based on MPNet (Masked and Permuted
Pre-training for Language Understanding), 110 million parameters, embedding
dimension of 768, maximum sequence length of 384 tokens, training via
contrastive learning on 1B+ sentence pairs, and state-of-the-art performance
on semantic textual similarity benchmarks (STS-B score of 86.4).

Advantages over BERT include bidirectional context as MPNet combines benefits
of BERT and XLNet, longer context handling with 384 tokens optimized compared
to BERT's 512, and semantic specialization through fine-tuning specifically for
sentence embeddings.

4.3 Sentiment Analysis: VADER with Chunk-Based Processing

The system implements VADER (Valence Aware Dictionary and sEntiment Reasoner)
for sentiment scoring through an eight-step algorithm (sentiment_analyzer.py
lines 40-73).

First, documents are split into 1600-character chunks (approximately 450
tokens). Second, a maximum of 4 chunks per document are processed to control
latency. Third, text is cleaned by removing metadata labels such as Content,
Comments, and Score. Fourth, each chunk is scored using the VADER polarity
lexicon. Fifth, VADER labels are mapped to normalized scores where LABEL_0
(negative) becomes -1.0 times confidence, LABEL_1 (neutral) becomes 0.0, and
LABEL_2 (positive) becomes +1.0 times confidence. Sixth, chunk scores are
averaged for document-level sentiment. Seventh, document scores are aggregated
for topic-level sentiment. Finally, categorization occurs where positive is
above 0.25, negative is below -0.25, and neutral is between these values.

VADER advantages include being lexicon-based requiring no training with
interpretable results, optimization for social media handling emoji, slang, and
capitalization, fast inference at 1000+ documents per second on CPU, and
robustness working well even with noisy text.

Limitations include context insensitivity as it cannot detect sarcasm or
nuanced sentiment, English-only functionality with no multilingual support, and
a static lexicon that cannot adapt to domain-specific language.

An alternative considered was CardiffNLP/twitter-roberta-base-sentiment
(transformer-based), which was tested but showed no significant accuracy
improvement while requiring GPU and demonstrating 10 times slower inference.

4.4 Keyword Extraction with Redundancy Filtering

The system implements a novel redundancy filtering algorithm (BertTopic.py
lines 548-693) that outperforms raw TF-IDF keywords through a seven-step
process.

First, initial ranking extracts top-N words per topic using TF-IDF scores.
Second, phrase prioritization identifies multi-word phrases (n-grams). Third,
component filtering removes single words that appear in higher-weighted
phrases. Fourth, lemmatization uses WordNetLemmatizer to detect plural/singular
variants. Fifth, stem matching compares first 3-4 characters to identify
related words. Sixth, weight-based selection keeps higher-weighted variants
when conflicts arise. Finally, length preference favors longer, more specific
terms when weights are equal.

For example, raw TF-IDF might produce "ring", "rings", "oura ring", "sleep",
"sleeping", "track", and "tracking", while filtered output yields "oura ring",
"sleep", and "tracking", reducing from 7 to 3 keywords.

The impact is a 40-60% reduction in keyword redundancy while improving human
interpretability.

4.5 Topic Summarization with LLMs

After extracting keywords and clustering documents, the system generates human-
readable summaries using LLMs through prompt engineering
(util/prompts/topic_prompt.py). The prompt instructs the model to analyze
social media discussions and generate a concise 1-sentence topic label plus a
2-3 sentence detailed summary, providing keywords, representative content, and
focus areas, with output formatted as JSON containing short_summary and
long_summary fields.

LLM selection (util/llm_models/llm_provider.py lines 21-89) uses Claude 3.7
Sonnet as primary with temperature of 0.1 for consistency, OpenAI GPT-4o as
first fallback if Claude unavailable, and Google Gemini 2.0 Flash as second
fallback if both unavailable.

Content selection extracts up to 25 representative paragraphs per topic
(increased from 10 in version 1.0), limits to maximum 30,000 characters per
summary request, and performs semantic similarity-based deduplication with
Jaccard threshold of 0.7.

5. VECTOR DATABASE IMPLEMENTATION

5.1 PostgreSQL pgvector Architecture

The system uses pgvector (version 0.5.1 or higher), a PostgreSQL extension
providing native vector operations with SIMD acceleration.

The schema (pgvector.py lines 38-70) creates the vector extension, defines a
reddit_embeddings table with id as UUID primary key with default random UUID
generation, subreddit as TEXT not null, post_id as TEXT not null, and embedding
as vector with 768 dimensions. An index reddit_embeddings_idx is created on
reddit_embeddings using ivfflat with embedding vector_cosine_ops and 100 lists.

5.2 IVFFlat Indexing

IVFFlat (Inverted File with Flat compression) provides approximate nearest
neighbor (ANN) search through a three-phase algorithm.

The training phase performs K-means clustering of embeddings into 100 centroids
(lists). The indexing phase assigns each vector to the nearest centroid. The
query phase searches only vectors in K nearest centroid lists.

Parameters include lists set to 100 (optimal for 10K-1M vectors per pgvector
documentation) and probes defaulting to 1 (can increase for higher recall at
cost of latency).

Performance characteristics include index build time of O(n times lists times
iterations) approximately 2 minutes for 100K vectors, query time of O(n divided
by lists) approximately 5-20ms for top-K equals 25, and memory overhead of
approximately 20-30% of raw vector storage.

An alternative considered was HNSW (Hierarchical Navigable Small Worlds) which
provides better recall but requires more memory (2-3 times overhead) and slower
indexing.

5.3 Embedding Storage Pipeline

The data flow (pgvector.py lines 91-206) follows five steps. First, text
extraction combines post title, content, and all comments. Second, embedding
generation performs batch encoding with SentenceTransformer with batch_size of
100. Third, deduplication checks existing post_ids to avoid redundant storage.
Fourth, batch insertion inserts 100 embeddings per transaction for atomicity.
Finally, explicit commit occurs after each batch for progress tracking.

Storage optimization includes compression via PostgreSQL TOAST automatically
compressing vector columns, partitioning not yet implemented (future work for
multi-tenant scenarios), and vacuuming handled automatically via autovacuum
daemon.

5.4 Semantic Search Implementation

Query execution (pgvector.py lines 207-246) selects id, post_id, subreddit,
and distance calculated as embedding cosine distance to query_embedding from
reddit_embeddings where subreddit matches case-insensitively, ordered by
distance and limited to top_k results.

The distance operator (<=>) computes cosine distance (1 minus cosine_similarity).

Performance tuning includes index usage confirmed via EXPLAIN ANALYZE, top-K
selection defaulting to 25 for good recall/precision balance, and subreddit
filtering using B-tree index on subreddit column for fast filtering.

5.5 RAG (Retrieval-Augmented Generation) Pipeline

The system implements RAG for contextual question answering (pgvector.py lines
248-335) through a six-step algorithm.

First, query encoding encodes the user question with SentenceTransformer.
Second, vector search retrieves top-K equals 15 most similar post_ids from
pgvector. Third, data enrichment joins with reddit_posts and reddit_comments
tables. Fourth, tree reconstruction rebuilds nested comment structure using
parent_comment_id. Fifth, context assembly formats posts and comments as
structured JSON. Finally, LLM generation passes context to Claude, GPT, or
Gemini for answer generation.

The prompt template instructs the model to answer based on customer feedback
from the specified subreddit, formatting the RAG context and user query, and
requesting evidence from specific posts and comments in the response.

Advantages over pure LLM include grounded responses citing specific customer
posts, scalability working with datasets too large for LLM context windows,
privacy keeping sensitive data in database with only relevant excerpts sent to
LLM, and freshness reflecting most recent data without model retraining.

6. LLM INTEGRATION ARCHITECTURE

6.1 Multi-Provider Abstraction Layer

The system implements a provider-agnostic LLM interface (llm_provider.py lines
21-89) supporting three commercial APIs.

Anthropic Claude 3.7 Sonnet (model claude-3-7-sonnet-20250219) provides 200K
context with cost of $3.00 per million input tokens and $15.00 per million
output tokens, used for topic summarization and RAG.

Anthropic Claude 4 Sonnet (model claude-sonnet-4-20250514) provides 200K
context with cost of $6.00 per million input tokens and $30.00 per million
output tokens, used for complex journey mapping.

OpenAI GPT-4o (model gpt-4o-2024-08-06) provides 128K context with cost of
$2.50 per million input tokens and $10.00 per million output tokens, used for
general content generation.

Google Gemini 2.0 Flash (model gemini-2.0-flash-exp) provides 1M context with
cost of $0.075 per million input tokens and $0.30 per million output tokens,
used for high-throughput tasks.

Provider selection logic attempts the requested provider if specified, falls
back to Claude if available, falls back to OpenAI if Claude unavailable, falls
back to Gemini if both unavailable, and returns error if no providers available.

6.2 AI Agent Orchestrator

The Agent Orchestrator (mcp-services/agent/app.py) serves as the central
intelligence hub with five key responsibilities.

Conversation management maintains per-session message history. Tool discovery
performs automatic detection of available MCP services. Tool execution handles
JSON-RPC invocation with parameter validation. Response generation uses Claude-
based natural language responses. Error handling implements graceful
degradation and retry logic.

The system prompt architecture (app.py lines 234-391) uses a dynamic system
prompt including service descriptions for all 14 applications, detailed
parameter schemas for each tool, usage examples with realistic scenarios,
guidelines for tool selection and sequencing, and error recovery strategies.

An example tool call flow proceeds as follows: User requests "Analyze sentiment
about Tesla on Reddit", Agent parses intent and selects social_topic_model
tool, sends JSON-RPC Request with method tools/call and parameters containing
name social_topic_model and arguments with subreddit teslamotors and num_posts
500, Social MCP Service validates parameters and forwards to backend, Backend
executes topic modeling pipeline and returns results, Agent formats results and
generates natural language summary, and User receives human-readable insights
plus visualization links.

6.3 WebSocket Communication

The Launchpad service (launchpad/app.py) implements a thread-safe WebSocket
proxy with five key features.

Bidirectional streaming flows from user messages to agent to MCP services to
agent to user. Connection pooling supports 100+ concurrent WebSocket
connections. Automatic reconnection detects agent disconnections and retries.
Message buffering queues messages during brief disconnections. Error recovery
sends error messages to client without breaking connection.

Thread synchronization uses a WebSocketProxy class with client_lock and
agent_lock as threading.Lock objects. The forward_to_agent method acquires
agent_lock before sending to agent_ws. The forward_to_client method acquires
client_lock before sending to client_ws.

Performance characteristics include latency under 50ms proxy overhead,
throughput of 1000+ messages per second per connection, and reliability of
99.9% message delivery with automatic retry on failure.

7. DATA PROCESSING PIPELINE

7.1 Reddit Data Collection

The system uses PRAW (Python Reddit API Wrapper) for data acquisition
(reddit_fetcher_topic_model.py lines 23-365) with six key features.

Recursive comment traversal fetches all nested comments using replace_more with
limit None. Date range filtering uses Unix timestamp-based filtering for
historical analysis. Rate limiting respects Reddit API limits of 60 requests
per minute. Keyword search supports subreddit-wide keyword queries. Image
processing optionally integrates GPT-4o Vision for image URLs. Cancellation
support implements thread-safe cancellation via Event objects.

The data structure includes id, title, content, score, created_utc timestamp,
url, permalink, num_comments count, author, and comments array. Each comment
contains id, body, score, created_utc, author, and nested replies array.

7.2 Asynchronous Job Processing

Topic modeling jobs are processed asynchronously to avoid request timeouts
through a six-phase job lifecycle.

Submission phase occurs when user initiates topic modeling via frontend. Job
creation phase has backend create job record in PostgreSQL with status pending.
Background execution phase uses Celery or threading to execute topic modeling
pipeline. Progress updates phase changes job status to processing, completed,
or failed. Result storage phase saves topic data to filesystem (JSON) and
database. Notification phase has frontend poll job status endpoint every 2
seconds.

The database schema includes jobs table with id as UUID primary key, type as
VARCHAR(50), status as VARCHAR(20), progress as INTEGER, result_path as TEXT,
error_message as TEXT, created_at as TIMESTAMP, and updated_at as TIMESTAMP.

7.3 Data Preprocessing

The text cleaning pipeline follows five steps. First, lowercasing normalizes
case for consistency. Second, stopword removal uses NLTK stopwords, scikit-
learn stopwords, and 30 custom terms. Third, token filtering removes URLs,
special characters, and optionally numbers. Fourth, lemmatization applies
WordNetLemmatizer for morphological normalization. Finally, N-gram extraction
uses CountVectorizer with ngram_range of (1,3).

Custom stopwords (BertTopic.py lines 761-767) include structural terms like
"title", "content", "comments", "https", "com", "www", and high-frequency
function words like "like", "just", "get", "know", "don", "really", "think",
"going", "want", "got", "would", "one", "also", "even", "much", "way", "make",
"see", "need", "well", "lot", "time", "good", and "people".

The rationale is to remove structural metadata and high-frequency function
words that don't contribute to topic semantics.

7.4 Error Handling and Logging

The system implements comprehensive error handling with four logging levels:
DEBUG for parameter values and intermediate results, INFO for job status
changes and tool executions, WARNING for fallback to defaults and missing
optional parameters, and ERROR for API failures, database errors, and
exceptions.

Log destinations include console via StreamHandler for development, filesystem
with rotating file logs (maximum 100MB, 5 backups), and database storing
critical errors in error_logs table.

Error recovery strategies include retry with exponential backoff for transient
API failures, graceful degradation using cached results or simplified
alternatives, user notification with clear error messages and suggested actions,
and automatic rollback where database transactions ensure atomicity.

8. PERFORMANCE ANALYSIS AND SCALABILITY

8.1 Benchmark Results

Topic Modeling Performance on Intel Xeon E5-2680 v4 with 128GB RAM shows the
following results:

For 100 documents: UMAP time 2.3 seconds, HDBSCAN time 0.8 seconds, LLM
summarization 15.2 seconds for 10 topics, total time 18.3 seconds.

For 500 documents: UMAP time 8.7 seconds, HDBSCAN time 2.1 seconds, LLM
summarization 42.6 seconds for 25 topics, total time 53.4 seconds.

For 1000 documents: UMAP time 15.2 seconds, HDBSCAN time 4.3 seconds, LLM
summarization 68.9 seconds for 35 topics, total time 88.4 seconds.

For 5000 documents: UMAP time 124.8 seconds, HDBSCAN time 18.7 seconds, LLM
summarization 312.4 seconds for 80 topics, total time 455.9 seconds.

Vector Search Performance on PostgreSQL 16 with pgvector and NVMe SSD shows:

For 10K embeddings: index build 12 seconds, query latency p50 of 8ms, query
latency p99 of 23ms, throughput 120 QPS.

For 100K embeddings: index build 98 seconds, query latency p50 of 12ms, query
latency p99 of 41ms, throughput 85 QPS.

For 500K embeddings: index build 512 seconds, query latency p50 of 18ms, query
latency p99 of 68ms, throughput 55 QPS.

For 1.5M embeddings: index build 1847 seconds, query latency p50 of 26ms,
query latency p99 of 102ms, throughput 38 QPS.

Sentiment Analysis Performance using CPU-based VADER shows:

For 100 documents with average 500 character length: processing time 0.8
seconds, throughput 125 documents per second.

For 1000 documents with average 500 character length: processing time 7.2
seconds, throughput 139 documents per second.

For 10000 documents with average 500 character length: processing time 68.4
seconds, throughput 146 documents per second.

Key observations include: UMAP dominates topic modeling time for large datasets
at 50-60%, LLM summarization is the bottleneck for many topics at 40-60% of
total time, vector search scales sub-linearly due to IVFFlat indexing, and
VADER sentiment analysis scales linearly with excellent throughput.

8.2 Scalability Architecture

Horizontal scaling strategies include five approaches:

Service replication via Docker Compose supports multiple replicas per service.
For example, social-research-backend can deploy with replicas set to 3 and
resources limited to 2 CPUs and 8GB memory.

Load balancing uses Nginx reverse proxy to distribute requests across replicas.

Database connection pooling employs SQLAlchemy with pool_size of 20 and
max_overflow of 10.

Async processing uses FastAPI with asyncio for non-blocking I/O.

Caching via Redis for frequently accessed data is planned but not yet
implemented.

Vertical scaling limits include memory requirements of approximately 500MB per
1000 documents for topic modeling, CPU scaling where UMAP benefits from multi-
core (scales to 8-16 cores), GPU acceleration where SentenceTransformer gains
3-5 times speedup with CUDA, and storage needs of approximately 3GB for 1
million embeddings (768 times 4 bytes times 1M).

8.3 Optimization Techniques

Implemented optimizations include five key techniques:

Batch embedding processes 100 documents per SentenceTransformer call.

Memory management uses explicit garbage collection after each topic via
gc.collect().

Lazy loading loads embeddings on-demand rather than in-memory.

Index optimization uses IVFFlat with optimal list count (square root of N).

Connection reuse maintains persistent database connections with pooling.

Future optimizations include five planned improvements:

ONNX conversion will export SentenceTransformer to ONNX for 2 times inference
speedup.

Quantization will use 16-bit float embeddings (384 dimensions) for 50% storage
reduction.

Approximate PCA will replace UMAP with faster PCA for large datasets.

Streaming processing will process documents in mini-batches to reduce memory.

HNSW migration will upgrade from IVFFlat to HNSW for better recall at scale.

10. FUTURE RESEARCH DIRECTIONS

10.1 Short-Term Enhancements (3-6 months)

Multi-lingual support will replace all-mpnet-base-v2 with multilingual-E5-
large, add language detection via langdetect library, and implement language-
specific stopword lists.

Active learning for topic refinement will present ambiguous documents to human
annotators, use feedback to adjust HDBSCAN min_cluster_size, and iteratively
improve topic boundaries.

Real-time topic tracking will implement online BERTopic updates via incremental
clustering, detect emerging topics via temporal analysis, and provide an alert
system for sudden sentiment shifts.

Advanced sentiment models will fine-tune RoBERTa on domain-specific data,
implement aspect-based sentiment analysis, and add emotion classification for
joy, anger, fear, and other emotions.

10.2 Mid-Term Research (6-12 months)

Zero-shot topic classification will use Claude or GPT to generate topic labels
without examples, combine with semantic search for topic discovery, and
eliminate the need for clustering in some scenarios.

Causal analysis will implement causal inference using the DoWhy library,
identify drivers of sentiment changes, and enable A/B test analysis for product
changes.

Graph neural networks for topic relationships will replace force-directed
layout with GNN embeddings, learn hierarchical topic structure, and enable
drill-down from broad to specific topics.

Federated learning for privacy will train models on distributed customer data,
aggregate model updates without sharing raw data, and comply with GDPR and data
residency requirements.

10.3 Long-Term Vision (12-24 months)

Multimodal foundation models will provide unified embeddings for text, images,
and video, enable cross-modal retrieval (finding images from text queries), and
support end-to-end multimodal topic modeling.

Autonomous agent workflows will implement Claude Code-style autonomous task
execution, create self-healing systems that debug and fix errors, and generate
proactive insights without user queries.

Causal reinforcement learning will learn optimal intervention strategies (such
as when to respond to negative sentiment), simulate customer behavior under
different scenarios, and optimize for long-term customer satisfaction metrics.

Neuromorphic computing will port embedding models to neuromorphic chips (Intel
Loihi), achieve 100 times energy efficiency for vector search, and enable real-
time processing of streaming data at scale.
